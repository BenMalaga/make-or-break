Command injection got the server to run attacker-chosen commands by slipping shell metacharacters into a parameter that was already being handed to a shell. A file upload arrives at the same destination, code running on the server, by a different road. Instead of smuggling a command into an existing call, the attacker delivers a whole file and then persuades the server to execute that file as a program. The avatar uploader on a profile page is the classic doorway.

An unrestricted file upload is any feature that accepts a file, writes it somewhere the server can reach, and never properly checks what the file actually is. The risk is not the act of uploading. It is what the server later does with a file it is willing to interpret. On a PHP application, a file whose name ends in .php and whose contents are PHP source is not data at all. It is a program, and the server runs it the instant a browser requests its URL.

The payload the attacker plants is a web shell. A web shell is a short script that reads a value out of the incoming request, passes it to the operating system, and returns whatever the system printed back into the response. One of them, dropped in the right place, turns a photo uploader into a remote command console. That is remote code execution, the same prize command injection chases, delivered as a file rather than a parameter.

Two conditions have to hold for the planted file to fire. The file has to land somewhere the server treats as executable code, and the attacker has to reach that location with an ordinary HTTP request. Break either link and the upload is inert. A PHP script saved outside the web root, or saved inside a folder configured to hand files back as plain downloads, is just text taking up disk space.

## The check that runs in the wrong place

The first defense most uploaders ship is a client-side check. A snippet of JavaScript inspects the chosen filename, sees that it does not end in .jpg or .png, and refuses to submit the form. On screen it looks like a real gate. It is not.

The browser belongs to the attacker. Every line of that JavaScript runs on the attacker's own machine, where it can be edited, disabled, or skipped entirely. The simplest bypass never touches the page. An intercepting proxy such as Burp Suite sits between the browser and the server, so the attacker submits an innocent image, then rewrites the paused request to swap in the .php file before it reaches the server. The validation code never sees the real upload.

The rule this teaches is old and absolute. A check that runs in the browser is a usability feature, not a security control. Anything the server needs to trust has to be decided by the server, on the bytes it actually received.

## Server-side filters and the bypass menu

A server that does validate still tends to validate the easy, wrong thing. Each shortcut has a matching bypass, and they are worth knowing as a set rather than one at a time.

The content-type check trusts the Content-Type header that came with the upload. That header is set by the client, so it lies on request. The attacker keeps the .php filename and simply sends Content-Type: image/png. The bytes are still PHP source; the server now believes they are an image.

The extension blocklist rejects a list of dangerous endings and allows everything else. This is backwards. A blocklist has to name every executable extension in advance, and web servers interpret more of them than most developers remember: .php3, .php4, .php5, .phtml, .phar, .pht. Miss one and the upload runs. An allowlist that permits only .jpg, .png, and .gif fails safe, because anything not on the short list is refused by default.

The double-extension trick targets servers that decide how to handle a file by scanning its name loosely. A file called shell.php.jpg ends in .jpg, so a naive suffix check is satisfied, yet a misconfigured Apache that runs any file containing .php in its name still executes it. Case games play the same angle. A filter that blocks .php but not .pHp leaves the door open on a case-insensitive filesystem.

The magic-byte check is the smart one, and it still falls to a polyglot. Here the server reads the first bytes of the file to confirm a real image signature. The attacker prepends a genuine header, GIF89a; is the favorite because it is short and printable, and places the script after it. The file is a valid GIF and a valid PHP script at once. The image parser reads the header and approves, while the PHP engine ignores the leading bytes and runs the code that follows.

Not every dangerous upload is a server-side shell. An SVG is XML that the browser renders, so an SVG carrying a script tag becomes stored cross-site scripting the moment another user opens it, and an uploaded HTML page served inline does the same. That file never runs on the server. It only needs the victim's browser to treat it as active content, which is why the type of file an application accepts matters as much as where it stores it.

## Where the file lands decides everything

Every bypass above only matters because of what happens after the save. A web shell is inert until the server executes it, so the storage decision is the control that outranks the filters.

Three properties of the destination matter. Whether it sits inside the web root, so a URL maps to it at all. Whether the directory is configured to execute scripts or to serve them as static bytes. And whether the attacker can learn or guess the final path. An application that writes uploads to a folder the web server refuses to interpret has already won, no matter how clever the polyglot was, because the request for shell.php comes back as source text instead of running.

This is also why locating the file is part of the attack, not an afterthought. Applications rename uploads, bury them under dated directories, or serve them from a path that never appears on the page. If the saved file cannot be reached over HTTP, the code inside it never runs, which is exactly the property a good defender engineers on purpose.

## Building an uploader that cannot be turned into a shell

Defense stacks. No single control is trusted alone, because each one has a known bypass, and the aim is to make every bypass land against another wall.

The strongest control is to validate by decoding and re-encoding, not by reading names or headers. An image upload is loaded into an imaging library and written back out as a fresh file. Re-encoding rebuilds the pixels and discards anything that was not part of the image, which destroys a GIF89a polyglot outright, because the smuggled PHP was never image data and does not survive the round trip.

Store uploads outside the web root, or in a location where the server will not execute code. A directory served as static downloads, with the script engine switched off, means a planted .php file is handed back as plain text. This is the layer that survives after a filter has already failed, which is why it carries the most weight in the stack.

Randomize the stored filename and discard the client-supplied name. A random identifier removes the attacker's ability to predict or reach the file, and it prevents a double-extension name from ever being written to disk.

Serve user files from a separate domain. A dedicated, cookieless host for uploads means that even a file that somehow executes cannot read the main application's session cookies or ride its trust, which contains the blast radius of anything that slips through. An allowlist of extensions, a size cap, and a nosniff header on the response finish the job by turning the rare bypass into a dead end rather than a foothold.

A web shell makes the server run commands the attacker chose. There is a quieter way to make the server act on the attacker's behalf, one that needs no upload at all: a feature that asks the server to fetch a URL, and the server, sitting inside the network, reaches somewhere the attacker never could from outside. That is where SSRF begins.
