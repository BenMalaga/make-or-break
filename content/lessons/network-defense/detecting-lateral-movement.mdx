An attacker almost never lands where they want to end up. They phish a helpdesk account, get a shell on some workstation with no useful access, and then the real work starts: moving sideways, host to host, hunting for credentials and reach until they get to the domain controller or the database that actually matters. That sideways journey is lateral movement, and it is your best chance to catch them, because it takes time and it generates traffic that normal users simply never produce.

The core insight for detection is that workstations do not talk to each other. Your accountant's laptop has no reason to open an SMB session to the marketing intern's laptop, or to RDP into a server it has never touched. When it suddenly does, that is not normal, and normal is the baseline you hunt against. Attackers have to move through the network, and the shape of that movement is different from how humans and applications behave.

## What movement looks like on the wire

Watch for one host reaching many others on the ports used for remote administration. SMB on 445, RDP on 3389, WinRM on 5985 and 5986, WMI over RPC. A single workstation opening 445 to fifty other hosts in ten minutes is a sweep, and no employee does that by hand.

The pattern that gives it away is fan-out. One source, many destinations, same admin port, short time window. Legitimate admin tools do this too, which is why you allowlist your known management hosts and then treat everyone else doing it as an incident.

## The techniques and their tells

Pass-the-hash lets an attacker authenticate with a stolen NTLM hash instead of a password. On the network it shows up as NTLM authentication from a host or account that should be using Kerberos, and as the same account logging into many machines in quick succession. In Windows logs, watch Event ID 4624 with logon type 3 (network logon) landing on hosts that account never touches, especially with an NTLM authentication package.

Remote service creation is a classic execution technique. Tools like PsExec create a service on the target to run their payload, which lights up Event ID 7045 (a new service was installed) and 4697. A new service named with random characters, installed on a host at an odd hour, from a source that is not your patch management system, is a strong signal.

Internal recon comes before the movement. Before an attacker can pivot, they enumerate: who is a domain admin, which machines exist, where the shares are. That means LDAP queries against the domain controller, DNS lookups for internal hosts in bulk, and SMB enumeration. A workstation firing hundreds of LDAP queries about group membership is casing the place.

<Callout type="security" title="Practice detection on your own data">
Building and testing these detections means generating lateral movement in a lab and watching your sensors catch it. Do that on a range you control or an authorized red-team engagement. Running these techniques on a production network you do not have written authorization to test is a crime, even if your intent is to check the alerting.
</Callout>

## Build detections around impossible-for-users behavior

Signatures for specific tools break the moment the attacker renames the binary or writes their own. So anchor detections on behavior that is hard to change and rare for real users. Workstation-to-workstation SMB. A service account, which should only run a service, logging in interactively. One account authenticating to twenty hosts in five minutes. A machine that has never used RDP suddenly making outbound 3389 connections across the subnet. None of those depend on the attacker using a named tool, and all of them are the movement itself.

<CommandCard command='index=windows EventCode=4624 Logon_Type=3 | stats dc(ComputerName) as hosts by Account_Name | where hosts > 10' explain="A Splunk-style search that counts how many distinct hosts each account did a network logon to. An account hitting more than ten machines in the search window is either an admin tool you should allowlist or an attacker spraying credentials. Tune the threshold to your environment, then alert on the rest." />

The trap is drowning in your own admin traffic. Your backup service, your vulnerability scanner, your patch deployment, and your monitoring agents all fan out to many hosts by design, and they will trip every detection above if you do not account for them. Inventory those systems first, allowlist them explicitly, and then anything left doing high fan-out is worth a human's attention. A detection that fires on legitimate ops noise gets muted, and a muted detection catches nobody.
