The socket in Sockets and Networking did one thing. It opened a TCP connection
to a single port and reported back whether anything was listening. One port, one
answer. A real target has 65,535 ports, and the interesting ones sit wherever the
services happen to be. Checking them by hand is not a plan.

A port scan is the act of trying to connect to a range of ports on a host to see
which ones accept a connection. An open port means a program on that host is
listening there, ready to talk. Finding the open ports is usually the first
useful thing anyone learns about a target, because a port that answers is a door,
and a door is where the work starts. A scanner is the loop that finds them. Two
questions turn one socket into that loop: how to ask about many ports, and how to
stop spending so much time waiting.

## The check, as a function

The socket lesson connected with `connect`, which raises an exception when the
port refuses. For a scanner that is the wrong shape, because a refused port is
not an error, it is a result. The socket module has a quieter version:
`connect_ex` returns a number instead of throwing. Zero means the connection
succeeded. Anything else is the operating system's error code for why it did not.
Wrapping that in a function gives a single, reusable check:

```python
import socket

def scan(target, port):
    sock = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    sock.settimeout(1)
    result = sock.connect_ex((target, port))
    sock.close()
    return result == 0
```

`settimeout(1)` is the load-bearing line. Without it, a port that never answers
would hang the socket for the operating system's default, which can be a minute
or more. With it, the socket gives up after one second and moves on. That timeout
is the single biggest control over how a scan behaves, and the rest of this lesson
keeps coming back to it.

A scanner is now just this function called across a range of ports:

```python
target = "scanme.nmap.org"
for port in range(1, 1025):
    if scan(target, port):
        print(f"{port} open")
```

`range(1, 1025)` covers ports 1 through 1024, the block where most well-known
services live: 22 for SSH, 80 for web, 443 for HTTPS. This loop works. It is also
slow, and the reason it is slow is worth understanding before reaching for a fix,
because the fix only makes sense once the waste is clear.

## Where the second goes

The speed of this loop depends entirely on what the ports do when contacted, and
they do one of three things. An open port completes the connection fast.
`connect_ex` returns 0 almost instantly. A closed port is nearly as quick: the
host sends back a TCP reset, a packet that means "nothing is listening here," and
`connect_ex` returns an error code right away. Neither of those is the problem.

The problem is the third case. A filtered port sits behind a firewall configured
to drop the connection attempt silently, sending nothing back at all. The socket
has no way to know the difference between "still thinking" and "will never
answer," so it waits the full one-second timeout before giving up. One second
does not sound like much. Multiply it by a few hundred filtered ports and the
scan crawls. A range of 1,000 ports where most are filtered spends over sixteen
minutes doing nothing but waiting, one idle second at a time.

That is the key insight. The slow part of scanning is not computing anything. It
is a program sitting still, blocked, waiting for a reply that a firewall has
already decided never to send.

## Overlapping the waiting

If the scanner spends its time waiting, the fix is to wait on many ports at once.
While one check is stuck on a filtered port's timeout, nothing stops another
check from firing off its own connection. That overlap is the entire idea behind
threading a scanner.

A thread is a second line of execution inside the same program, able to run while
another line is blocked. Python has a well-known catch here called the Global
Interpreter Lock, or GIL: a rule that stops two threads from running Python code
at literally the same instant. For work that is all computation, that lock makes
threads nearly pointless. Scanning is the opposite of computation. It is
I/O-bound, meaning it spends almost all its time waiting on input and output, in
this case the network. And CPython releases the GIL while a thread is blocked
inside a socket call. So while one thread sits inside `connect_ex` waiting for a
reply, the lock is free and another thread runs its own connect. The work that
overlaps is the waiting, which is nearly all of the work.

Managing threads by hand is fiddly. `ThreadPoolExecutor` from the standard library
does it instead: hand it a function and a list of inputs, and it runs the function
across a fixed pool of worker threads, keeping the pool busy until the inputs run
out.

```python
import socket
from concurrent.futures import ThreadPoolExecutor

target = "scanme.nmap.org"
open_ports = []

def scan(port):
    sock = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    sock.settimeout(1)
    if sock.connect_ex((target, port)) == 0:
        open_ports.append(port)
    sock.close()

with ThreadPoolExecutor(max_workers=200) as pool:
    pool.map(scan, range(1, 1025))

print(sorted(open_ports))
```

`pool.map(scan, range(1, 1025))` hands each port to the next free worker. With
200 workers, up to 200 sockets are waiting on their timeouts at the same time, so
the whole sweep finishes in the length of the slowest few timeouts rather than the
sum of all of them. A scan that took sixteen minutes serial drops to a few seconds.

Two details keep this correct. The `with` block matters: leaving it waits for
every worker to finish before the `print` runs, so `open_ports` is complete when
it is read. And the shared `open_ports.append` is safe here only by luck of the
implementation. In CPython a single list append is atomic, so two threads
appending at once cannot corrupt the list. Any operation more involved than that
would need a lock, and a program that assumes threads can scribble on shared data
freely is a bug waiting to surface.

More workers is not always faster. Every open socket costs a file descriptor, and
operating systems cap how many a process may hold at once, often around 1,024 by
default. Push `max_workers` into the thousands and the scanner starts failing to
open sockets, or the target's own rate limiting starts dropping the flood and
skewing the results. Somewhere between 100 and 300 workers is a sane band for most
scans. Faster past that point usually means less accurate, not more.

## Making the result useful

An open port number is a lead, not an answer. Port 22 is almost certainly SSH,
but "almost certainly" is not knowledge, and a service can run on any port its
owner chose. The way to learn what is actually listening is to read the first
thing it says. Many services announce themselves the instant a connection opens:
SSH sends its version string, FTP and SMTP send a greeting line. Reading those few
bytes is called grabbing the banner.

```python
def scan(port):
    sock = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    sock.settimeout(1)
    if sock.connect_ex((target, port)) == 0:
        try:
            banner = sock.recv(1024).decode(errors="ignore").strip()
        except OSError:
            banner = ""
        open_ports.append((port, banner))
        print(f"{port:>5} open  {banner}")
    sock.close()
```

The `try`/`except OSError` is not defensive boilerplate, it is doing real work.
Not every service greets a new connection. A web server, for one, says nothing at
all until the client sends a request first. So `recv` on port 80 sits there with
nothing to read, waits out the one-second timeout, and raises an exception. Without
the `except`, that exception would kill the check and drop port 80 from the results
even though it is wide open. Catching it lets the port still register, just with an
empty banner. `decode(errors="ignore")` handles the other rough edge: a banner is
raw bytes, some of which are not valid text, and ignoring the bad ones keeps a
stray byte from crashing the scan.

Run against a host that is explicitly cleared for scan testing and the output
names the services directly:

<Callout type="security" title="A scan is an action against a real machine">
A port scan is active reconnaissance. It opens real connections, it shows up in
the target's logs, and in many places scanning a host without permission is a
crime, not a gray area. The only legitimate targets are a lab the operator owns, a
box under their control, or a host with written authorization to test.
`scanme.nmap.org`, used above, is a machine the nmap project publishes
specifically for scan practice, at a gentle rate.
</Callout>

<Callout type="tip" title="This will never beat nmap, and it is not meant to">
nmap does everything here and far more: it fingerprints services precisely,
handles half-open scans, and paces itself against defenses. A hand-rolled scanner
is for understanding what nmap does underneath, and for the odd host where dropping
a binary is off the table but Python is already present.
</Callout>

To feel the real difference, change `target` to `scanme.nmap.org` in both and run

length of one.

A working scanner prints open ports to a screen. That is a tool, not a program
someone else can run. Automating Recon takes this scanner and gives it a real
interface: `argparse` for proper flags, targets read from a file, results written
as JSON or CSV instead of print statements, error handling for hosts that vanish
mid-scan, and rate limiting so the scan stays a good citizen on the network.
