The previous lesson put a single value into a variable and read it back by name, one value sitting under one label. Most real scripting work is not about one value. It is about a whole batch of things at once: every number in a range, every file in a folder, every process running on a machine. PowerShell's answer to "do something to all of these at once" is the pipeline, and it is the single idea that does the most work in the whole language.

## The heart of PowerShell

A pipeline connects one cmdlet's output straight into the next cmdlet's input, written with the pipe character, `|`. Whatever the first cmdlet produces becomes the raw material the second cmdlet works on, and a pipeline can chain several cmdlets in a row, each one refining what came before it.

What actually moves through that pipe is an object, a chunk of data with named fields attached to it, never a printed line of text. A range of numbers is the simplest place to see this:

```powershell
1..5 | ForEach-Object { $_ * $_ }
```

<ExpectedOutput label="each number in the range squared">
```
1
4
9
16
25
```
</ExpectedOutput>

`1..5` builds a range counting from one to five. The pipe hands each number, one at a time, to `ForEach-Object`, which runs the script block in curly braces once per number that arrives. Inside that block, `$_` stands for whatever object is currently passing through that stage. On the first pass `$_` is 1, and `$_ * $_` is 1. On the last pass `$_` is 5, and `$_ * $_` is 25. Nothing gets typed out five separate times. The same short block runs once per item, automatically, and the pipeline moves on to the next item without being told to.

That `$_` variable is worth sitting with, because it shows up in nearly every pipeline a PowerShell script writes. It has no meaning sitting on its own outside a pipeline stage. Inside one, it always means "the object this stage is looking at right now," and a field on that object can be reached with a dot after it, the way `$_.CPU` would reach the CPU field of whatever process object happens to be flowing through at that moment.

## Where-Object: keeping only what matches

Filtering, keeping some objects and dropping the rest, is `Where-Object`'s job. It runs a script block against every object arriving from upstream, and lets through only the ones where that block's condition comes out true:

```powershell
1..10 | Where-Object { $_ -gt 7 }
```

<ExpectedOutput label="only the numbers greater than 7 survive">
```
8
9
10
```
</ExpectedOutput>

Ten numbers went in. `Where-Object` tested each one against `$_ -gt 7` and threw away every number that failed the test, so three numbers came out the other side. Nothing about the surviving numbers changed; they are the same 8, 9, and 10 that went in, untouched. `Where-Object` only decides what continues on, never what a surviving object looks like once it gets there.

Real process data behaves the same way. `Get-Process` returns one process object for every running program on the machine, and each of those objects carries a `CPU` field showing how much processor time that program has used:

```powershell
Get-Process | Where-Object { $_.CPU -gt 10 } | Sort-Object CPU
```

That line reads almost like plain English once its pieces are named: get every process, keep only the ones whose CPU field is greater than 10, then put whatever is left in order by that same field. The exact processes that come back, and their CPU numbers, depend entirely on what happens to be running on the machine at that moment, so there is no single fixed answer to print here the way there was for a fixed range of numbers. That variability is normal for anything reading live system state rather than a value a script built itself.

## ForEach-Object: doing something to each one

`Where-Object` only filters. When each object needs to become something else, run through a calculation, or get folded into a new piece of text, `ForEach-Object` is the cmdlet built for that. It runs its script block once per incoming object and passes along whatever the block produces:

```powershell
1..3 | ForEach-Object { "Item number $_" }
```

<ExpectedOutput label="each number rewritten as a labeled string">
```
Item number 1
Item number 2
Item number 3
```
</ExpectedOutput>

Three numbers went in, three strings came out. Each pass used `$_` inside a double-quoted string, so the string interpolation from the previous lesson picked up the current number and dropped it straight into the sentence. `ForEach-Object` is the general-purpose "run this on every item" cmdlet, and its output does not have to keep the same shape as its input. It can shrink an object down to a single number, expand a number into a full sentence, or run any calculation in between.

Filtering and transforming together is one of the most common shapes a pipeline takes:

```powershell
1..10 | Where-Object { $_ -gt 5 } | ForEach-Object { $_ * $_ }
```

<ExpectedOutput label="numbers greater than 5, each one squared">
```
36
49
64
81
100
```
</ExpectedOutput>

Ten numbers arrive. `Where-Object` keeps only 6 through 10. `ForEach-Object` then squares each of those five survivors. Running the two cmdlets in the other order would square every number from 1 through 10 first, then test the squared results against `-gt 5`, which throws away only 1 and 4 instead of the numbers 5 and under. Order matters, because each stage only ever sees what the stage before it decided to pass along.

## Select-Object: fewer fields, or fewer objects

Not every field on an object is useful for the task at hand, and not every object in a long pipeline needs to be looked at. `Select-Object` trims a pipeline in either of those two directions. Given one or more property names, it keeps only those fields on each object flowing through:

```powershell
Get-Process | Select-Object -First 3 Name
```

<ExpectedOutput label="illustrative: the first three process objects, showing only their Name field (the actual names depend on what is running)">
```
Name
----
pwsh
node
Finder
```
</ExpectedOutput>

Two things happen in that single line. `-First 3` cuts the pipeline down to the first three objects that reach it, regardless of how many process objects existed in total before that point. `Name` then narrows each of those three surviving objects down to just its Name field, dropping every other field the object was carrying, such as its process ID or its CPU time. The exact three names shown depend on what happens to be running when the line executes, but the shape of the result does not change: one column, three rows.

`-First N` on its own, without naming any property, is worth reaching for often. A long list of files, processes, or results rarely needs to be read in full while a pipeline is still being worked out, and cutting it down to the first handful during testing saves scrolling past pages of objects that were never the point.

## Sort-Object: putting objects in order

Filtering decides what stays in a pipeline. Sorting decides what order it comes out in. `Sort-Object` takes a property name and reorders everything flowing through by that field, smallest value first by default:

```powershell
5, 2, 8, 1 | Sort-Object
```

<ExpectedOutput label="plain numbers sorted smallest to largest">
```
1
2
5
8
```
</ExpectedOutput>

With no property named, `Sort-Object` compares the objects directly, which works fine for plain numbers like these. Objects carrying several fields need to say which one to sort by, which is exactly what `Sort-Object CPU` did earlier: order the surviving process objects by their CPU field specifically, rather than by their name or their process ID. Adding `-Descending` after the property name flips the order to largest first, which is the more useful direction the moment the real question changes from "smallest first" to "which one is using the most."

## Measure-Object: doing the arithmetic

Once a pipeline holds the right objects in the right order, a common next step is a single number that summarizes all of them: a total, an average, the largest one seen. `Measure-Object` calculates exactly that, in one pass, without a hand-written loop or a running total variable to manage:

```powershell
1..10 | Measure-Object -Sum -Average -Maximum
```

<ExpectedOutput label="Measure-Object's summary of the numbers 1 through 10">
```
Count    : 10
Average  : 5.5
Sum      : 55
Maximum  : 10
Minimum  :
Property :
```
</ExpectedOutput>

`-Sum` adds every number in the pipeline together. `-Average` divides that total by how many numbers there were. `-Maximum` reports the largest single value seen. All three ran over the same single pass through the ten numbers, so one line of code produced a count, a sum, an average, and a maximum together. `-Minimum` is available the same way, it was simply left off this call, which is why that line comes back blank instead of showing a value.

On a collection of full objects rather than plain numbers, `Measure-Object` needs to be told which field to measure, the same way `Sort-Object` needed a property name:

```powershell
Get-Process | Measure-Object CPU -Sum -Average
```

That adds up and averages the CPU field across every running process object, with results that shift depending on what is running at the time, exactly like the earlier `Get-Process` examples. What never shifts is why the calculation works at all: `Get-Process` handed over real objects with a CPU field already attached as a number, so `Measure-Object` could read that field by name and do arithmetic on it directly. Nothing had to be split out of a printed column or converted from text first. A traditional shell that only passed lines of text between commands would need a separate parsing step before any of that arithmetic could even begin.
